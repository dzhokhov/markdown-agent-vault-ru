# Протокол обработки 00_inbox/

## Суть

`00_inbox/` — зона разбора, не мусор. Файлы попадают сюда из разных источников (email, telegram, ручной импорт, скрипты). Агент, обработавший файл из inbox, **обязан** записать результат обработки в лог. Без записи в лог обработка считается незавершённой.

Это решает главную проблему: владелец не знает, какие файлы в inbox уже обработаны и безопасны для удаления, а какие ещё не тронуты.

---

## Лог обработки

Файл: `00_inbox/PROCESSING_LOG.md`

### Формат записи

```markdown
## 2026-03-31

- **source:** `00_inbox/youtrack-issues/` (234 файла)
  **action:** Импортировано в 01_now/projects/2026-acme-crm-rollout/tasks.md
  **result:** Все задачи перенесены, исходники безопасны для удаления
  **status:** ✅ processed
  **agent:** Claude (Cowork session)

- **source:** `00_inbox/2026-03-05-ai-agents-implementation-meeting.md`
  **action:** Извлечены решения → 01_now/projects/2026-acme-crm-rollout/log.md, контакты → 03_knowledge/contacts-network/
  **result:** Полностью разобрано
  **status:** ✅ processed
  **agent:** Claude (meeting-processing skill)
```

### Статусы

| Статус | Значение |
|--------|----------|
| ✅ processed | Полностью обработано, исходник можно удалить |
| 🔄 partial | Частично обработано, нужна доработка |
| 👀 reviewed | Просмотрено, решено оставить как есть (без переноса) |
| ⏳ queued | Запланировано к обработке, ещё не тронуто |

## Обязательные действия агента

### При работе с файлом из 00_inbox/

1. **Обработай** — извлеки ценное, перенеси куда нужно (`01_now`, профильный `01_now/ops/<contour>`, `03_knowledge`). `02_domains` — legacy-слой, не использовать без прямой просьбы владельца.
2. **Запиши в лог** — добавь запись в `00_inbox/PROCESSING_LOG.md`
3. **НЕ удаляй исходник** — удаление только по решению владельца

### При массовой обработке (дампы, импорты)

1. Укажи общее количество файлов и что именно извлечено
2. Если обработана только часть — статус `🔄 partial` с указанием что осталось

### При работе с выгрузкой Telegram

1. Все разовые и обновляемые выгрузки сообщений Telegram храни только в отдельных подпапках `00_inbox/telegram-dumps/`. Таблицы, справки и другие результаты обработки можно переносить в постоянные разделы, но сырые сообщения остаются только здесь.
2. Срок хранения выгрузки — 14 календарных дней с момента последнего содержательного обращения к ней, которое сопровождалось успешной догрузкой свежих сообщений.
3. Содержательным обращением считается использование сообщений для поиска, анализа или подготовки ответа. Проверка наличия файла, просмотр списка папок и служебная проверка хранилища обращением не считаются.
4. При каждом содержательном обращении до начала анализа проверь существующую выгрузку и `.smart-env/telegram-reader-state.json`, затем догрузи сообщения, появившиеся после последней успешной выгрузки. Не скачивай историю заново, если сохранённый указатель позволяет продолжить выгрузку.
5. После успешной догрузки обнови сопроводительный `.meta.json`: `last_used_at` — время обращения, `last_synced_at` — время успешной догрузки, `expires_at` — дата и время удаления, равные `last_used_at + 14 дней`. Если у старой выгрузки нет сопроводительного файла, создай его в той же подпапке.
6. Если догрузить свежие сообщения не удалось, сохранённую выгрузку можно использовать только с явным предупреждением о дате её последнего обновления. `last_used_at` и `expires_at` в этом случае не обновляй.
7. По наступлении `expires_at` автоматически удаляется только соответствующая подпапка выгрузки. Созданные на её основе постоянные документы и таблицы не удаляются.
8. Исключения допускаются только отдельной строкой в [реестре очистки](../cleanup-registry.md). Общий срок не применяется к каноническим полным снимкам, необработанным аудиозаписям, расшифровкам и другим явно зарегистрированным исключениям.
9. Не сохраняй рядом с сообщениями ключи API, строку Telegram-сессии и другие секреты.

### При vault review

1. Прочитай `00_inbox/PROCESSING_LOG.md`
2. Предложи владельцу удалить файлы со статусом ✅ processed
3. Файлы без записи в логе = необработанные, не предлагать к удалению

## Что НЕ нужно логировать

- Автоматические дампы, которые перезаписываются (`telegram-dumps`, `web-dumps`), — у них свой срок хранения в [реестре очистки](../cleanup-registry.md). Содержательное использование Telegram-выгрузки и успешная догрузка фиксируются в сопроводительном `.meta.json`; отдельная запись в `PROCESSING_LOG.md` для продления срока не нужна.
- Email-inbox — управляется через SQLite в zimbra_inbox_fetcher.py
- Файлы, которые агент только прочитал, но не обрабатывал (консультация ≠ обработка)
