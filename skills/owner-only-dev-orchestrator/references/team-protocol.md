# Протокол команды

## Продуктовые и технические функции

| Функция | Пишет | Не имеет права |
|---|---|---|
| Владелец продукта | Продуктовую рамку или отчёт об отклонении | Детализировать функции, выбирать архитектуру и менять цель без человека-владельца |
| Продуктолог | Продуктовое решение и приоритеты | Менять рамку, выбирать техническое устройство и объявлять собственное решение принятым |
| Архитектор | Документ решения | Одобрять своё решение |
| Архитектурный критик | Только отчёт вне проверяемого файла | Исправлять решение |
| Исправляющий архитектуру | Документ решения | Менять цель и критерии критика |
| Разработчик | Код и тесты в своей рабочей копии | Разрешать выпуск |
| Независимый тестировщик | Только отчёт и результаты команд | Исправлять код или ослаблять тест |
| Исправляющий после тестов | Код в своей рабочей копии | Закрывать собственный дефект |
| Технический документатор | Документацию | Описывать непроверенное как готовое |

## Правила передачи

Каждая передача содержит цель, точную версию входа, применимые критерии, разрешённые пути записи и требуемый формат результата. Продуктолог получает точную продуктовую рамку, а архитектор — рамку и принятое продуктовое решение; устного пересказа недостаточно. Передача проверки дополнительно называет независимого тестировщика, точную фиксацию Git и конкретный неизвестный, устаревший либо неуспешный исход, который нужно получить заново. Не передавай критику оправдание автора. Не сворачивай первый вердикт до передачи исправляющему.

## Продуктовый переход

- Новый продукт или смена цели: владелец продукта → продуктолог → тот же владелец продукта в режиме проверки отклонения.
- Существенная возможность внутри действующей рамки: продуктолог → владелец продукта в режиме проверки.
- Принятая возможность или чисто техническая правка: продуктовые роли пропускаются с явным основанием.
- Обе продуктовые роли сначала предлагают решение. Они могут передать человеку-владельцу один компактный блок вопросов с рекомендуемыми ответами, но не просят его писать бриф или требования с нуля.
- Перед архитектурой требуется `PASS` владельца продукта на точной версии продуктового решения. После существенного пользовательского результата тот же агент сравнивает демонстрацию с рамкой, не повторяя тесты.
- Не более двух содержательных продуктовых циклов без нового факта или решения человека-владельца.

## Условия перехода

- Архитектура принята только после отсутствия блокирующих замечаний на текущей версии.
- Продуктовое решение принято только после `PASS` владельца продукта на текущей версии.
- Код принят только после независимого результата `PASS` на текущей фиксации.
- Новая фиксация требует новой независимой проверки, но её глубина определяется составом разницы и текущей точкой приёмки.
- `INCOMPLETE` не равен успеху.
- Документация и подготовка отката выполняются после проверки кода.
- Слияние не равно выпуску.

## Соразмерность маршрута

- Продуктовый маршрут определяется изменением пользователя, ценности, основного сценария, границ и продуктовой приёмки; технический риск сам по себе его не включает.
- Локальный код внутри принятой архитектуры проходит разработчика и независимого тестировщика; архитектурный цикл не повторяется без изменения устройства системы.
- Новая архитектура, модель состояния, схема данных, границы компонентов, безопасность, внешние зависимости и труднообратимые решения проходят архитектора, критика и при необходимости исправляющего архитектуру.
- Высокий риск усиливает доказательства и ограничения выпуска, но не создаёт автоматического требования повторять незатронутые роли.
- Чисто документальная фиксация получает отдельную независимую проверку разницы, ссылок, команд и неизменности исполняемых путей. Полный прогон выполняется, только если изменены код, тесты, сборка, настройки выполнения, машинно читаемые входы или текущая точка приёмки прямо его требует.
- Любое изменение кода остаётся независимо проверяемым. Автор не принимает собственный результат.

## Препятствия и заметный результат

Каждое препятствие помечается как блокирующее разработку, слияние либо выпуск. Выпускная проверка на устройстве не останавливает безопасную обратимую разработку автоматически. Каждый рабочий цикл называет один наблюдаемый пользовательский результат и способ его показать.

## Предел циклов

Не более трёх циклов архитектуры и трёх циклов исправления кода по одной причине. После этого зафиксируй красный статус, корневую причину и безопасное предложение: сократить область, сменить решение или получить новое решение владельца, если меняется продуктовая цель.

Для технического сбоя роли действует другой предел: один активный агент функции на одном входе и не более одного повторного запуска. Истечение ожидания не является сбоем. До соразмерного ориентира времени активный статус достаточен для продолжения; после него требуются свежие подтверждения: сообщение, процесс или новый результат в задаче либо Git. Если остаётся только неизменный статус, управляющий один раз запрашивает состояние, ждёт ещё не менее половины исходного ориентира и не менее 5 минут, затем повторяет проверку. Прерывание допустимо только при явной ошибке, остановленном агенте либо одновременном отсутствии свежего сообщения, процесса и нового результата после двух проверок. Перед прерыванием фиксируются идентификатор агента, запуск, последний прогресс, оба снимка состояния и исход запроса; полезные изменения сохраняются. Параллельные дубликаты одной функции запрещены.

## GitHub

- одна задача → одна ветка → один запрос на слияние;
- обязательные проверки относятся к конечной фиксации;
- новые изменения делают прежнее одобрение устаревшим;
- незакрытые обсуждения блокируют слияние;
- основная ветка не переписывается принудительно;
- внешнее действие выполняется только после решения владельца.
