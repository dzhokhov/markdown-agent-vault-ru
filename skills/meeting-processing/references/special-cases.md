# Особые случаи и Шаг 7.5 FIELD_NOTES

Примеры вымышленные: контуры `acme-shop` и `beta-corp`, компания «Acme», люди «Анна П.», «Виктор С.».

## Особые случаи

### Встреча без транскрипта (заметки / пересказ)

Пользователь описывает встречу словами, без файла:
- Шаг 1 (EXTRACT) выполняй по рассказу пользователя.
- Задавай уточняющие вопросы по каждому слою: «Были ли конкретные решения? Кто что взял на себя? Какие цифры обсуждались? Что-то упомянули вскользь, что может всплыть позже?»
- Дальше — стандартный pipeline начиная с Шага 2.

### Встреча, затрагивающая несколько контуров

- Основной контур = где больше решений и действий.
- Файл саммари → в основном контуре.
- В `log.md` каждого затронутого контура → короткая запись со ссылкой на основное саммари.
- Делегирования → в папку делегирований **контура самого делегата** (не обязательно основного контура встречи). Пример: на встрече контура acme-shop Виктор С. из контура beta-corp взял задачу → строка идёт в `delegations/viktor-s.md` контура beta-corp.
- Задачи агента → в `tasks.md` соответствующих проектов.

### Повторяющиеся встречи (синки, стендапы)

Для регулярных встреч отдельный файл саммари каждый раз не нужен. Достаточно:
- запись в `log.md` (3–5 строк);
- классифицированные строки в `plan.md` / `tasks.md` / delegations / personal;
- эпизодика: мало — инлайн в log.md под хэштегом; много — создать файл саммари;
- строка журнала взаимодействий (модуль, если объявлен).

Отдельный файл создавай, только если на регулярке обсуждалось нетипичное: стратегическое решение, крупная проблема, смена курса.

### Отсутствие `plan.md` у затронутого проекта (legacy)

Строка «ушла бы в `plan.md`», а проект его не имеет → создай `plan.md` из [шаблона](../../../meta/templates/project_plan.md) при первом касании, перенеси `Goal` / контекст цели из `README.md` или `tasks.md`, затем добавь новое решение. В `log.md` проекта одна строка: «создан plan.md при миграции в task-routing-модель».

### Встреча по личному обязательству (вне контура)

Встреча вне проектного контура (юрист, врач, ремонт, бытовая консультация) — головной папки нет. Решения, обещания владельца, даты → `personal/tasks.md §Hard`. Эпизодика — короткой заметкой в `00_inbox/`. Повторяется → предложи владельцу создать персональный контур и головную папку.

## Шаг 7.5. FIELD_NOTES — атомарные наблюдения (встречи с внешними участниками)

Выполняется **после** основного pipeline (EXTRACT → ... → LINK) и **только** для встреч с внешними участниками (клиенты, партнёры, бета-тестеры, подрядчики) — встреч, приносящих наблюдения о рынке, клиентах, индустрии. Для внутренних синков команды шаг пропускается.

### Зачем

Основной pipeline фиксирует **проектные** артефакты: решения, задачи, метрики. Встреча с внешним участником приносит также **знания о мире** — как устроен бизнес клиента, какие паттерны на рынке, что работает и что нет. Эти знания живут дольше любого проекта и ценны для других контуров.

Методология — Atomic Research (Pidcock): цепочка experiments → facts → insights → recommendations, наблюдения фиксируются атомарно и без смешивания факта с интерпретацией. Confidence ladder — [write-protocol.md §1.1](../../../meta/rules/write-protocol.md).

### Алгоритм

1. **Перечитай транскрипт** с фокусом: «Что нового я узнал о рынке / клиенте / индустрии / технологиях — помимо проектных решений?»
2. **Извлеки атомарные наблюдения** по модели Pidcock:
   - **Fact** — наблюдение без интерпретации: что человек сказал или сделал. Цитата или близкий парафраз; кто сказал и в каком контексте.
   - **Insight** — интерпретация: что это может значить для проекта / продукта / рынка. Явно пометь как интерпретацию.
   - **Recommendation** — следствие: что с этим делать. Допустим open question вместо готового решения.
3. **Оцени объём**: наблюдений ≥3 → отдельный файл полевых заметок. 1–2 → добавь в карточку организации/человека в секцию «Заметки».
4. **Создай файл полевых заметок** (если ≥3 наблюдений):
   - место: база знаний хранилища; имя: `field-notes-<тема>-<YYYY-MM>.md`;
   - frontmatter: `confidence: single-source` — всегда для одной встречи ([write-protocol.md §1.1](../../../meta/rules/write-protocol.md));
   - структура: тематические секции, каждое наблюдение с Fact + Insight + контрпримером для проверки;
   - секция «Открытые вопросы для следующих встреч» — обязательна.
5. **Заполни профиль организации по таксономии** (если встреча с агентством / компанией-клиентом):
   - карточка организации — в реестре контактов базы знаний; нет карточки → создай по шаблону профиля организации, если шаблон есть в реестре;
   - секция «Профиль по таксономии» — оси отраслевой таксономии участников рынка (классификация типов компаний по осям бизнес-модели); неизвестные оси помечай ❓;
   - таксономии в базе знаний нет → пропусти пункт с пометкой «пропущено: нет таксономии».
6. **Маршрутизация**:
   - полевые заметки → база знаний;
   - проектные следствия → ссылка из `context.md` проекта на полевые заметки;
   - open questions → `plan.md` проекта или полевые заметки (по значимости);
   - `log.md` проекта: одна строка «field notes: [ссылка], N наблюдений, confidence: single-source».
7. **Перекрёстная проверка**: есть другие файлы `field-notes-*` по схожей теме → проверь пересечения. Наблюдение совпало с наблюдением из другого источника → повысь `confidence` в обоих файлах до `emerging`.

### Пример (вымышленный)

Встреча с агентством «Acme» (2026-04-16) → основной pipeline дал саммари + задачи + карточки. Шаг 7.5 дополнительно создал: файл полевых заметок об операциях агентства (14 наблюдений, 3 секции), профиль компании по осям таксономии и ссылку из `context.md` контура на полевые заметки.
