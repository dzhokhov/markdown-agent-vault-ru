# AGENTS.md — правила агента для файлового хранилища

## Главный принцип

Это хранилище работает только тогда, когда до каждого важного документа можно добраться через указатели, ссылки и правила маршрутизации.

Если агент создаёт или меняет файл, он обязан обновить связанные индексы и кратко зафиксировать решение в нужном журнале.

## Карта папок

| Папка | Назначение |
|---|---|
| `00_inbox/` | Новые и ещё неразобранные материалы |
| `01_now/` | Активная работа: проекты, текущие области, личные задачи |
| `02_domains/` | Прежний раздел; новые постоянные области создаются в `01_now/ops/` |
| `03_knowledge/` | Переиспользуемые знания, методологии, справка |
| `04_logs/` | Хронология, обзоры, журналы решений |
| `90_archive/` | Завершённое и устаревшее |
| `meta/` | Правила, шаблоны, служебные индексы |
| `skills/` | Скиллы: инструкции для повторяющихся типов задач |

## Первый запуск

Хранилище требует первичной настройки, если отсутствует `meta/config/contours-map.md` или `meta/config/agent-profile.md` либо один из этих двух файлов имеет `status: template`. Если оба имеют `status: active`, первичная настройка завершена. Шаблонные `tracker-profile.md` и `writing-canons.md` допустимы: их настраивают отдельно при необходимости. Настройку выполняй по [vault-setup](./skills/vault-setup/SKILL.md).

## Загрузка контекста

Перед ответом агент определяет тип задачи и читает минимальный нужный контекст:

| Тип задачи | Что читать |
|---|---|
| Активный проект | `01_now/projects/<project>/README.md`, затем `context.md`, при необходимости `plan.md`, `tasks.md`, `log.md` |
| Постоянная область | `meta/config/contours-map.md`, затем `01_now/ops/<контур>/README.md` |
| Справка или методология | `03_knowledge/README.md`, затем нужный файл |
| Запись или изменение файла | `meta/rules/write-protocol.md` |
| Маршрутизация задач | `meta/rules/task-routing.md` |
| Контурный GitHub-репозиторий | `repository-manifest.yml` + `meta/rules/github-contour-repositories.md` |
| Создание нового проекта | `skills/project-creator/SKILL.md` + `03_knowledge/ai/agent-plan-methodology-research-2026-07.md` |
| Актуальная память проекта или контура | `meta/rules/vault-memory.md` |
| Сжатие истории встреч | `skills/context-compression/SKILL.md` |
| Обработка входящих материалов | `meta/rules/inbox-processing.md` |
| Проверка и уборка хранилища | `meta/rules/vault-review.md` |
| Создание временных файлов | `meta/rules/cleanup-by-design.md` |
| Недосказанный или многовариантный запрос | `03_knowledge/ai/agent-intent-reconstruction-instruction-2026-06.md` |

Если контур или проект неоднозначен, агент задаёт один короткий вопрос на уточнение и не читает содержательные файлы разных контуров подряд.

Если в корне рабочей папки есть `repository-manifest.yml`, агент обязан прочитать его сразу после `AGENTS.md`. Для такого режима действует правило [контурных GitHub-репозиториев](./meta/rules/github-contour-repositories.md): "можно без вопроса" означает подготовить ветку и заявку на изменение, а не менять основную ветку напрямую.

## Недосказанные запросы

Если запрос можно выполнить несколькими существенно разными способами, агент сначала восстанавливает намерение владельца:

1. Что владелец явно попросил.
2. Какой практический результат ему нужен.
3. Какие ограничения видны из проекта, правил, языка сообщения и указанного пути.
4. Что можно безопасно предположить.
5. Где ошибка предположения испортит результат и нужен один короткий вопрос.

Безопасное предположение можно делать, если оно опирается на контекст, легко исправляется и не меняет смысл результата, контур, место записи, источник правды или глубину вмешательства.

Если ошибка в предположении может повредить данным, маршрутизации, приватности или будущей работе, агент задаёт один короткий вопрос и не начинает выполнять задачу наугад.

Внутренний разбор намерения не нужно показывать владельцу как отдельный отчёт. Он нужен для выбора глубины работы, места чтения и записи, формата результата и границ вмешательства. Полная методология: [инструкция восстановления намерения агента](./03_knowledge/ai/agent-intent-reconstruction-instruction-2026-06.md).

## Создание проекта

Новый активный проект создаётся через скилл [project-creator](./skills/project-creator/SKILL.md) в `01_now/projects/<год>-<slug>/`.

В проекте должны быть:

- `README.md` — вход, смысл и навигация;
- `plan.md` — цель, границы, намерение владельца, критерии качества, вехи, блокеры;
- `tasks.md` — текущая очередь исполнения;
- `context.md` — устойчивые знания проекта;
- `log.md` — короткая история решений.

`plan.md` хранит направление и вехи. `tasks.md` хранит только текущие действия. История не живёт в `tasks.md`; она живёт в `log.md`.

План и критерии качества пишет агент. Владелец не должен заполнять план, придумывать пункты или проверять его построчно. Если без уточнения нельзя безопасно выбрать цель, границы, источник правды или цену ошибки, агент задаёт один короткий пакет вопросов и предлагает рекомендуемый вариант.

Методология: [планирование для LLM-агента](./03_knowledge/ai/agent-plan-methodology-research-2026-07.md).

## Память

Архив не равен актуальной памяти. `log.md`, старые встречи, входящие материалы и черновики нужны для проверки источников, но не должны автоматически считаться текущим состоянием.

Актуальная память живёт в:

- `context.md` — устойчивые инварианты;
- `plan.md` — цель, границы, вехи, блокеры и защита от дрейфа;
- отдельной текущей картине, если проект или контур слишком длинный для одного `context.md`;
- профильных файлах решений, фактов или гипотез, если они объявлены источником правды.

Перед сложной задачей агент читает актуальные слои до архива. После значимого события обновляет `plan.md`, `context.md`, текущую картину, `log.md` и `tasks.md` в этом порядке, если эти слои затронуты.

Важные утверждения памяти не становятся истиной только потому, что записаны. Для решений, рисков, ограничений, текущих статусов и гипотез нужно фиксировать тип утверждения, источник, основание, уровень доверия, дату проверки и правило записи. Подробности: [Память vault](./meta/rules/vault-memory.md), [Антипамять](./meta/memory/anti-memory.md), [Журнал изменений памяти](./meta/memory/ledger.md).

## Контурный GitHub-репозиторий

Если задача относится к отдельному GitHub-репозиторию контура:

1. Прочитай `repository-manifest.yml`.
2. Проверь владельца, класс данных и разрешённые зоны.
3. Если действие затрагивает закрытые данные, правила доступа, удаление, перенос или другой контур — задай один короткий вопрос.
4. Готовь изменения через ветку и заявку на изменение, если прямое изменение основной ветки явно не разрешено.
5. В описании заявки напиши: что изменено, зачем, какие файлы затронуты, есть ли риск закрытых данных, какие проверки прошли и что должен подтвердить человек.

Подробности: [контурные GitHub-репозитории](./meta/rules/github-contour-repositories.md).

## После записи файла

После создания или существенного изменения файла агент проверяет:

1. Есть ли корректная служебная разметка в начале `.md` файла.
2. Обновлён ли `README.md` раздела.
3. Нужно ли обновить `plan.md`, `context.md`, текущую картину, `log.md` или `tasks.md`.
4. Работают ли относительные ссылки.
5. Найдёт ли новый агент этот файл через навигацию.
6. Нужна ли запись в [журнал изменений памяти](./meta/memory/ledger.md).
7. Есть ли план жизненного цикла для временных файлов.

## Скиллы

Скиллы лежат в `skills/<name>/SKILL.md`. Агент читает скилл только тогда, когда задача подходит под его описание.

Базовые скиллы:

- `project-creator` — создание нового проекта с автономным планом, стартовыми файлами и обновлением индексов;
- `meeting-processing` — обработка встреч и расшифровок;
- `context-compression` — сжатая историческая память встреч и ограниченное окно чтения;
- `research` — исследование и фиксация результата;
- `parking` — сохранение точки возврата;
- `resume` — возврат к сохранённой задаче;
- `new-dialog-handoff` — безопасный переход в новый чат;
- `owner-only-dev-orchestrator` — ведение задач разработки с минимальным участием владельца;
- `test-gates` — проверка изменений;
- `release-rollback` — выпуск и откат.

## Язык ответа

Агент отвечает на языке пользователя. Если использует технический термин, он объясняет его простыми словами при первом упоминании.

## Запреты

- Не создавать файлы без понятного места и назначения.
- Не оставлять важные документы без ссылки из указателей.
- Не хранить долгоживущие знания внутри временного проекта.
- Не складывать личные обязательства, делегирования и цели проекта в один список.
- Не удалять логи и входящие материалы без явной просьбы владельца.
- Не читать личную почту, мессенджеры или внешние сервисы без прямой просьбы.
- Не коммитить закрытые данные, секреты, сырые импорты и крупные исходники в обычный контурный репозиторий.

## Следующий шаг

Если это первый запуск, агент должен прочитать `START_HERE.md`, этот файл и `meta/rules/write-protocol.md`, затем кратко объяснить владельцу, как устроено хранилище.
